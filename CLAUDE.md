# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

See [GDD.md](GDD.md) for story/design intent — this file is architecture only.

## Running the Game

```bash
git clone --recurse-submodules https://github.com/umutcanekinci/artifical-chaos.git
cd artifical-chaos
uv sync
uv run python __main__.py
```

If you forgot `--recurse-submodules`: `git submodule update --init`.

### Building a distributable

`uv sync --group build && uv run pyinstaller artifical-chaos.spec --noconfirm`
produces a standalone onedir bundle in `dist/artifical-chaos/` (bundling
`assets/` — no `config/` tree here, see the plain-constants note below); the
tag-triggered `.github/workflows/release.yml` (`git tag v0.1.0 && git push
origin v0.1.0`, or "Run workflow" for a build-only dry run) builds Windows/
macOS/Linux zips, publishes a GitHub Release, and pushes each to itch.io
(`umutcanekinci/artifical-chaos`, needs a `BUTLER_API_KEY` repo secret).
Unlike chokepoint/highrise/hunted, `__main__.py` does **not** unconditionally
chdir into a resource root — that would contradict this file's own "assumes
cwd is the repo root" note for running from source (matches `pyproject.toml`'s
`pythonpath` and how CI invokes it). Instead it chdirs into `sys._MEIPASS`
*only* when `sys.frozen` is set (i.e. only inside a PyInstaller build, where
`artifical-chaos.spec` unpacks `assets/` there regardless of onedir/onefile
mode) — verified by actually running a local onedir build headlessly
(`SDL_VIDEODRIVER=dummy`) and confirming it stays up instead of crashing on
a missing asset path. No logo asset yet, so there's no icon-generation step
(unlike chokepoint's `scripts/make_icon.py`) — `artifical-chaos.spec` falls
back to PyInstaller's default icon until one exists.

## Testing

```bash
uv run --group dev pytest tests/ -q                      # this app's own logic tests
uv run --group dev pytest tests/ --cov --cov-report=term  # with coverage
cd src/pygamine && uv run --group dev pytest -q        # the vendored engine's own suite
uv run python scripts/smoke_test.py                       # headless boot check
uv run python scripts/balance_sim.py                       # 1v1 player/soldier-vs-drone time-to-kill sim
```

`.github/workflows/ci.yml` runs the pytest suites and smoke test (`engine-tests`, `app-tests`, `app-smoke-test`) on every push/PR, and auto-commits `.github/badges/coverage.json` (read by the README badge) after pushes to `main`. `scripts/balance_sim.py` isn't wired into CI (no assertions to fail on, just a table to read) -- it's a manual tool for sanity-checking `DRONE_TYPES`/`SOLDIER_CLASSES`/`PLAYER_FIRE_*` changes before committing to them, same discipline as GDD.md's drone-hp balance pass.

## Architecture

### Entry point → Game class

`__main__.py` inserts `src/` and `src/pygamine/` onto `sys.path`, then calls `Game().run()`. Unlike some sibling projects, this one does **not** `chdir` to a resource root first — it assumes cwd is the repo root (matches how `pyproject.toml`'s `pythonpath` config and CI both invoke it).

`Game` (`src/app/game.py`) extends `pygamine.Application` directly — no panel/scene system, no YAML config. `util/constants.py` holds plain Python constants (window size, sprite scale, tuning numbers) in place of the `config/settings.yaml` pattern used by chokepoint/highrise/standoff.

`Game` doesn't override `run()` at all for its splash screen anymore — `Application` itself now owns a `self.splash` slot (`None` by default) and calls `self.show_splash()` as the first thing `run()` does, a no-op if nothing's set; `Game.__init__` just constructs `self.splash = pygamine.SplashScreen(...)` and the base class picks it up automatically. Same fade/hold values (`SPLASH_FADE_MS`/`SPLASH_HOLD_MS`) chokepoint/highrise/hunted/standoff/terraria all use, though this project shows two images in sequence rather than their one: `assets/images/branding/pygame_logo.png` (the shared engine credit) then `assets/images/branding/title.png` (this game's own title card — AI-generated key art, not pixel-matched to the in-game sprites on purpose; see the credit/generation note in the Assets section below). `SplashScreen` advances through its image list automatically on fade+hold elapsed, or immediately on any keypress/click, so the second slide isn't stuck waiting the full duration if the player's already impatient. It's constructed in `__init__` (needs a display surface for `convert_alpha()`, already up by then); `show_splash()` runs it directly against `self.display_surface`/`self.clock`/`self._fps` rather than through `Application`'s own scaled `self.window`/`_present()` path — `SplashScreen.run()` calls `pygame.display.update()` itself each frame, so drawing onto the offscreen logical canvas instead would never actually reach the screen.

### Subsystems wired in `Game.__init__`

| Object | Class | Responsibility |
|--------|-------|----------------|
| `all_sprites` / `walls` / `flags` / `soldiers` / `robots` | `GameObjectList` (plain list subclass) | Per-category entity lists; `_purge_inactive()` drops anything with `.active = False` each frame |
| `map` | `Map(TiledMap)` (`gameplay/map.py`) | Loads `assets/images/tileset/tiledmap.tmx`, pre-renders tile layers scaled by `SCALE_FACTOR`, spawns `Flag`/`Drone`/`Soldier` from the Tiled object layer's `name` field (`"flag"`, `"spawnPoint"`) — each `"flag"` object spawns one drone and one soldier, the soldier round-robining through `SOLDIER_CLASSES` globally while the drone round-robins within its own flag's `FLAG_TIERS` band (see `spawn_objects()`'s two-pass structure below) — and spawns `Obstacle`s from tile collision shapes (see Obstacle below). `self.spawn_point` comes from the tmx's one `"spawnPoint"` object (a dedicated `"spawn"` objectgroup, away from every flag and any wall — verified against `game.walls` when it was placed); `Player`'s starting position uses this, not `map.rect.center`. The `"spawnPoint"` branch used to be missing the `* SCALE_FACTOR` the `"flag"` branch right above it has (a latent bug — the object itself didn't exist in the tmx yet, so it never actually ran), fixed when the object was finally added. `spawn_objects()` gathers every `"flag"`/`"spawnPoint"` object in one pass *before* spawning anything (rather than spawning inline as it iterates, the original approach) because `_rank_flag_tier_indices()` needs `spawn_point` known first — the tmx's object order doesn't guarantee `"spawnPoint"` comes before every `"flag"` — then ranks all flags by squared distance from it into `len(FLAG_TIERS)` roughly-equal bands (nearest third `FLAG_TIERS[0]`, i.e. `"Outpost"`) before the real second pass actually constructs `Flag`/`Drone`/`Soldier`. Falls back to the middle tier for every flag if `spawn_point` is somehow `None` rather than crashing, though every real map has one (see above). |
| `camera` | `FollowCamera(pygamine.Camera)` (`gameplay/camera.py`) | Adds `follow(target_center)` on top of the base edge-scroll/zoom camera — centers the target every frame, then clamps to map bounds |
| `player` | `Player` (`gameplay/player.py`) | The Squad Leader — see below |
| `tutorial` | `Tutorial` (`gameplay/tutorial.py`) | A one-shot, linear controls onboarding overlay — see below |

`Game.update()` sets `self.delta_time` from the clock (clamped to `MAX_DELTA_TIME`, `util/constants.py` — see below), calls `camera.follow(player position)`, updates every sprite, then the tutorial, then purges inactive ones. `self.keys` (used by `Player.walk()`/`Soldier.walk()`) is populated once per frame by `Application._listen_inputs()` — code that constructs `Player`/`Soldier` directly (e.g. tests) must supply a `game.keys` dict-like object itself; see `tests/conftest.py`'s `FakeGame`.

`self.delta_time = min(self.clock.get_time() / 1000, MAX_DELTA_TIME)` — the clamp is a fix for a real reproduced bug, not defensive-for-its-own-sake: `pygame.time.Clock.get_time()` measures wall-clock time since the *previous* `tick()` call, so anything that makes one frame take unusually long (measured: a `restart()` call, which re-parses the tmx and rebuilds every tile layer/spawn, takes about **1 second** in this codebase's own map) doesn't show up in that frame's own `delta_time` — it lands entirely inside the *next* frame's reading instead, since `tick()` doesn't know or care what happened between calls. `Player`/`Soldier`/`Drone.move()` is quadratic in `delta_time` (`velocity = acceleration * dt * ms`, then `position += velocity * dt`), so an unclamped ~1-second spike combined with a held movement key (very plausible right after mashing a restart click, since reflexes are often still holding a direction) moves an entity thousands of world units in one frame — tunneling clean through a wall (no continuous collision detection here, just a per-frame AABB overlap test) or landing outside the map/camera entirely, which is exactly what a player reported as "spawns in the wrong place" / "becomes hidden" right after a fast click-to-restart, and which reliably stopped once they let go of movement keys and waited before clicking (zero acceleration means the same giant `delta_time` multiplies out to nothing). `MAX_DELTA_TIME = 1/20` caps the worst case at a modest single-frame nudge instead of a teleport.

### Entities

- **Player** (`gameplay/player.py`): 8-directional movement with friction (`walk()` sets `acceleration`/`rotation` from `game.keys`, `move()` applies velocity + friction + AABB collision against `walls`), footprint trail (`Footprint`, spawned on a timer, grows then expires), recruits `Soldier`s within 50px (`get_soldier()`), rank counter with an insignia sprite. `rank_up()` is called by `Flag.update()` the instant a flag's progress hits 100% (not by recruiting or by kills), and now has a real effect: it picks `RANK_UP_STATS_FEW_RANKS` (2) distinct stats at random out of `{hp, speed, fire_rate, damage}` and buffs each by one step (`util/constants.py`'s `RANK_UP_*_BONUS`) — dropping to `RANK_UP_STATS_MANY_RANKS` (1) once a map has `RANK_UP_MANY_RANKS_THRESHOLD` (`MAX_RANK`, 15) or more flags, since a map with that many rank-ups will hit every stat naturally anyway; this map's 10 flags stay under that, so every rank-up here buffs 2 stats. `fire_damage`/`fire_cooldown_ms` moved from flat `PLAYER_FIRE_*` module constants (still the initial values, still used by `Soldier`-style per-instance-stat convention) to per-instance attributes on `Player` specifically so rank-ups can mutate them — `PLAYER_FIRE_RANGE` stays flat since range isn't one of the four rank-up stats. Each stat picked also spawns a `FloatingText` (`gameplay/effects.py`) at the player's position, offset sideways per pick so simultaneous picks don't overlap. `get_rank_image()`'s sheet-column formula is `5 + rank % 5` (`squad-insignia.png` is 240×216, i.e. 10×9 @`RANK_SIZE`, but only columns 5-9 are the insignia block) — it used to be `% 6`, reaching column 10 and raising a subsurface `ValueError` the moment `rank_up()` first got called for real (rank 5 onward), since nothing had ever called it more than once before `Flag.update()` started calling it on every capture; the rank used for the lookup (not `self.rank` itself) is also clamped to `MAX_RANK` as a second guard against the row math (`rank // 5`) overflowing the sheet's 9 rows past that. Fights with a sidearm: `shoot()` fires at the nearest drone in `game.robots` within `PLAYER_FIRE_RANGE` while the left mouse button is held, using `self.fire_damage`/`self.fire_cooldown_ms` (rank-scaled); `aim_at_mouse()` turns `facing` to face the cursor (cosmetic — hit resolution is range-based, not directional). If no drone is in range **or** the nearest one is behind a wall (`combat.has_line_of_sight()`), `shoot()` falls back to `fire_at_nothing()` instead of doing nothing at all (or, previously, hitting straight through the wall): same cooldown gate, but purely cosmetic — a `MuzzleFlash`+`Tracer` toward the mouse cursor always plays (the gun still visibly fires into empty space, in the aim direction rather than toward the blocked target), and a `combat.raycast()` toward that same aim point drops a `BulletImpact` decal (`gameplay/effects.py`) if the shot would have hit a wall. Unlike `Soldier`/`Drone`, a blocked target needs no special fallback-movement handling here — the player is directly controlled, so there's no autonomous approach behavior that could get stuck near an obstacle. `die()` (HP reaches 0, called by whatever damages the player) sets `is_dead`, zeroes velocity/acceleration, and plays the death clip; `update()` short-circuits once dead so the frozen death pose stays on screen instead of `self.active = False` removing the sprite. `squad_stance` (`"engage"` by default) is toggled by `toggle_squad_stance()`, bound to Tab via `Game.handle_event()` (an override of `pygamine.Application`'s empty per-event hook) — flips to `"guard"` and back, popping a `FloatingText` each time (`SQUAD_STANCE_LABELS`/`COLORS` in `util/constants.py`) as an immediate one-shot cue, plus `draw_squad_stance()` now keeps a persistent bottom-left HUD label showing the current stance at a glance (fixed to the screen, not the player's world position, unlike `draw_rank()`/`draw_health()`) — added because the popup alone was easy to miss if you looked away right when it fired. Purely a stance switch read by `Soldier.engage()` (see below), not a targeting command — the player never selects who a soldier shoots at.
- **Soldier** (`gameplay/soldier.py`): takes a `soldier_class` string (default `"Assault-Class"`) that looks up `hp`/`speed`/`fire_range`/`fire_damage`/`fire_cooldown_ms`/`splash_radius` from `SOLDIER_CLASSES` (`util/constants.py`) and picks the matching sprite sheet -- `hp` (`self.max_hp`) used to be a flat 100 for every class regardless of role, the same gap `DRONE_TYPES`' hp already had before its own first balance pass; a later pass gave Sniper-Class/RadioOperator-Class (least reason to be caught in a real fight -- long range, or no combat role at all) the lowest hp (70/80) and MachineGunner-Class/AntiTank-Class (shortest `fire_range`, so forced closest to danger) the highest (110/120), keeping Assault-Class/Grenadier-Class at the original 100 as the baseline — `Sniper-Class`, `MachineGunner-Class`, and `AntiTank-Class` are wired up the same way as `Assault-Class`, just with different stat blocks (long-range/high-damage, short-range/fast-cooldown, and high-damage/slow, respectively), all with `splash_radius: 0`. `Grenadier-Class` has `splash_radius: 90` and is the one class whose `attack()` takes the other branch: instead of `MuzzleFlash`+`Tracer`+single `apply_damage`, it spawns a `Grenade` (see Effects) that arcs to the target's position, then calls `combat.find_all_in_range(target.position, game.robots, self.splash_radius)` and damages every drone that comes back — so a cluster near the aim point all take a hit, not just the nearest one — followed by a `BigExplosion`. Damage still resolves the instant `attack()` runs (same hitscan-in-spirit convention as everything else in `combat.py`); the `Grenade`/`BigExplosion` are cosmetic on top, same as `Tracer` is for single-target hits. `splash_radius: 0` on every other class means `attack()`'s AoE branch never triggers for them — "by construction", the same idiom `DRONE_TYPES`' Hornet uses for `melee_range: 0`, not a special-cased `if soldier_class == "Grenadier-Class"` check. `RadioOperator-Class` is the other non-uniform class: `support_cooldown_ms: 15000` (every other class is 0, same "by construction" idiom again) makes `engage()` skip combat entirely and call `call_reinforcement()` instead — on that cooldown, it spawns a fresh `Soldier` of a random *other* combat-capable class (`support_cooldown_ms == 0`) at a small fixed-length random-direction offset (`RADIO_OPERATOR_REINFORCEMENT_OFFSET`) from itself, calls `add_to_army()` on it immediately (the same one-line join `Player.get_soldier()` gives a proximity-recruited soldier), and pops a `FloatingText` ("+SQUAD"). Picked over the GDD's other two suggested options for this ability: "reveal the map" has nothing to reveal (this game already has no fog of war), and a stat-boosting aura would need to track each buffed soldier's un-boosted base stats to undo the buff once it walks out of range — real complexity a first pass doesn't need. Idle until `add_to_army()` is called (by `Player.get_soldier()`); once recruited, `engage()` runs each frame instead of a plain follow — it finds/holds the nearest drone in `game.robots` within `self.fire_range` (facing/status/acceleration all update the instant one's in range, so it visibly aims) if one exists, otherwise falls back to the original chase-the-player-past-100px / hold-position behavior, and always separates from other soldiers within `AVOID_RADIUS` (`avoid_entities()`). The actual `attack()` call (gated by `self.fire_cooldown_ms` as always) additionally requires `game.player.velocity.length() < SQUAD_ATTACK_MAX_PLAYER_SPEED` — added because letting soldiers land hits while trailing a continuously-moving player made squad combat require zero player input/skill (see GDD.md's second balance pass); an in-range soldier now visibly aims but doesn't connect until the player actually stops, without changing *who* it targets, so the no-individual-micromanagement pillar stays intact — this only gates whether the already-autonomous targeting is allowed to land. A found target behind a wall (`combat.has_line_of_sight()` fails) is dropped back to `None` in the same pass as the guard-stance distance check, rather than held onto like the player-speed case — `Soldier` has no "walk toward my target" behavior of its own (only `Drone.engage()` does), so holding a blocked target would leave it frozen aiming at a wall forever; falling back to `walk()` instead means it keeps following the player, which changes the geometry over time instead of standing stuck. `walk()` takes an optional `hold_distance` (defaults to `SOLDIER_HOLD_DISTANCE`, 100 — the original hard-coded value) so `engage()` can tighten it: when `game.player.squad_stance == "guard"`, both the fallback `walk()` call and the target search itself change — hold distance drops to `SQUAD_GUARD_HOLD_DISTANCE` (40, a tight escort formation instead of ranging out ~100px) and a found target is discarded if it's more than `SQUAD_GUARD_ENGAGE_RADIUS` (150) from the player, even if well within the soldier's own (possibly much longer, e.g. Sniper's 450) `fire_range` — added because "guard" is meant to read as *protect the commander*, not *fight from wherever, just stand closer*. Neither check touches *which* target gets picked, only *where* the soldier's willing to look for one or how far it'll range out while idle, so the no-individual-micromanagement pillar holds the same way the stationary-fire gate does. Every `SOLDIER_CLASSES["speed"]` is deliberately higher than `Player.ms` (100) — `walk()`'s movement formula is quadratic in `ms` (`acceleration = direction * ms`, then `velocity = acceleration * dt * ms`, i.e. `~ms² * dt`), so a soldier with `ms <= 100` that falls behind a continuously-moving player can never close the gap again; a soldier standing right next to its spawn-adjacent guardian drone will still look "stuck" (correctly prioritizing that fight over following, per the no-micromanagement pillar), but once nothing's in range it reliably catches back up to the 100px hold distance. `avoid_entities()`'s push scales with how close the two soldiers are (`(AVOID_RADIUS - distance) / AVOID_RADIUS`, times `self.ms`) rather than a constant unit-length nudge — the old constant push wasn't strong enough up close to stop soldiers drifting into a visible overlap; exact-zero distance (two soldiers precisely co-located, where `Vector2.normalize()` would raise) is handled with a deterministic `id(self) < id(soldier)` tie-break so they push apart instead of both doing nothing. There's no player-directed command/targeting — every in-army soldier picks its own nearest target independently, purely a function of its own position, never the player's (a deliberate GDD pillar: no individual unit micromanagement). `draw_recruited_marker()` draws a green ring (`assets/images/ui/selection-circles.png`, row 1 col 0 of its 2×5 grid) under any `is_in_army` soldier, called from `Game.draw()` before the main sprite loop so it renders underneath the character — added because the 50px recruit radius (`Player.get_soldier()`) is easy to walk past without noticing, leaving a soldier still dormant with no other visual difference from a recruited one.
- **Drone / Scarab / Spider / Hornet / Wasp / Centipede** (`gameplay/robot.py`): `Drone` is the shared base class, taking a `drone_type` string that looks up stats (`hp`/`speed`/`melee_range`/`fire_range`/`melee_damage`/`fire_damage`/`melee_cooldown_ms`/`fire_cooldown_ms`) **and sheet layout** (`sprite_size`/`clip_rows`/`destroyed_row`) from `DRONE_TYPES` (`util/constants.py`) and picks the matching sprite sheet; five concrete classes are thin subclasses that just pin `drone_type`, and `DRONE_CLASSES` is the spawn-time lookup `map.py` uses. All run the same combat state machine each frame (`engage()`): idle until the player or an in-army soldier is within `AGGRO_RADIUS` (shared across types; `get_target()`, nearest-wins via `combat.find_nearest` — will chase a closer soldier over a farther player), then approaches; within `self.fire_range` **and** with `combat.has_line_of_sight()` clear, it fires; within the tighter `self.melee_range` (no line-of-sight check — already point-blank) it melees instead, each gated by its own cooldown. A target that's in `fire_range` but behind a wall doesn't get dropped, just denied the shot — `engage()` falls through to the same "walking" approach branch as being out of range entirely, so a blocked drone keeps closing distance (toward melee range, or until the sightline reopens) instead of standing still trading shots with a wall. Scarab/Spider share an 80×80 (5×5 @16px) idle/walk/fire/melee/destroyed sheet layout. Spider is a melee-only fast flanker: `fire_range`/`fire_damage` both `0` means the fire branch in `engage()` can never trigger (`distance <= 0` essentially never happens) -- the same "by construction" idiom Hornet/Wasp already use for `melee_range: 0`, just on the opposite stat. This isn't purely cosmetic: with the old `fire_range` (90) and `stand_off_range: 0` (no kiting), `engage()`'s fire branch zeroes acceleration the instant Spider got within it, so it would plant its feet and snipe weakly forever instead of ever actually closing the last stretch to `melee_range` -- a real mismatch with its own "prefers melee" GDD role, not just an unused stat. `melee_damage` was bumped a little (14 → 16) on top of the by-construction change to keep its overall threat up now that it has no ranged fallback at all; `scripts/balance_sim.py`'s simulated 1v1 pass confirmed this changes which soldier classes can solo it (Grenadier-Class, the lowest single-target-dps class, now loses where it used to win) but that's the melee rework doing its job -- Spider actually reaching melee now -- not a regression to chase. Hornet's sheet is actually 24×24 frames in an 8×2 grid (confirmed by rendering it with a grid overlay, since the layout isn't documented in the asset pack's info file) — `clip_rows` points `idle`/`walking` at row 0 (neutral hover) and `fire`/`melee` at row 1 (firing hover); `melee_range: 0` means the melee branch in `engage()` never fires (`distance <= 0` essentially never happens), so it's ranged-only by construction rather than by special-cased logic. `stand_off_range: 150` (every other type is 0, same "by construction" idiom — `engage()` branches on it being > 0) makes it actually kite: once a target closes inside that while still within `fire_range`, it backs away (`-delta.normalize() * self.ms`) instead of holding ground like every other drone at fire range, while continuing to fire the whole time. Wasp is 16×16, a single row — every `clip_rows` entry points at row 0, so all four statuses render identically (verified in `test_robot.py`). Neither Hornet nor Wasp has a destroyed frame (`destroyed_row: None`), so `has_destroyed_clip` is `False` for them and `die()` sets `self.active = False` immediately instead of holding a destroyed pose — `update()`/`die()` both guard on `self.active` so a drone deactivated mid-frame (e.g. by an attacker whose `update()` ran earlier the same frame) doesn't keep acting until `Game._purge_inactive()` removes it.

  `Centipede(Drone)` is the one drone type with a genuinely segmented body, added on top of the same base `Drone` (hp/combat/wall-collision on the head are all inherited unchanged) rather than a new architecture: `Centipede.__init__` spawns one `CentipedeSegment` GameObject per entry in `CENTIPEDE_SEGMENT_ROWS` (purely visual — no `hp`, not in `game.robots`, so never independently targetable/damageable) and `update()` walks the chain each frame calling `CentipedeSegment.follow(leader_position)`, which snaps each segment just enough to hold `CENTIPEDE_SEGMENT_GAP` from the one in front of it — a rigid constraint solved fresh every frame (not a spring), so segments hold a fixed distance instead of oscillating. Segments spawn already spaced out in a line behind the head's spawn point (not stacked on top of it), so an idle, undiscovered Centipede reads as a body immediately rather than looking like one ball until it first moves. `die()` deactivates every segment (and spawns an `Explosion` at each) the instant the head itself transitions from active to inactive — checked via a `was_active`/`not self.active` comparison around `super().die()` rather than a status flag, so a second `die()` call on an already-dead Centipede (idempotency, same as every other drone) doesn't re-trigger it. `Centipede.png` is 128×288 (8 cols × 18 rows @16px, confirmed by rendering it with a grid overlay): rows 0-3 are an armored head in 4 states, used for `idle`/`walking`/`fire`/`melee` in row order (nothing in the asset pack documents which row is "meant" to be which); rows 8-16 are plain round body-segment frames with no head armor, one row per segment (`CENTIPEDE_SEGMENT_ROWS`) purely for visual variety along the body — no destroyed frame, so it's removed immediately on death like Hornet/Wasp.
- **Flag** (`gameplay/flag.py`): pulses a separate animation loop (`draw_pulse`, not part of the normal `Animator`/update cycle since it's drawn directly by `Game.draw()`). Now has real gameplay behind it: `update()` (added to the normal cycle via `game.all_sprites`) fills `self.progress` (0–100) toward `self.captured = True` while `is_held()` (player or an in-army soldier within `FLAG_CAPTURE_RADIUS`, via `combat.find_nearest`) and not `is_contested()` (any drone within the wider `FLAG_CONTEST_RADIUS`); contested always wins over held, so decay happens even while the player is standing right on it. Progress never goes negative and never exceeds 100; once `captured`, `update()` short-circuits (locked in) and `draw_pulse()` stops drawing entirely (no pulse ring, no capture fill). `draw_pulse()` draws `_draw_capture_progress()` (an elliptical pie-slice fill, `gameplay/ui.draw_radial_progress`, centered on `rect.center`) *before* the pulse ring, and both run before `Game.draw()`'s main sprite loop — so the fill sits furthest back, the pulse ring in front of that, and the flag's own sprite in front of both, layered through draw order (not z-index). The fill itself is semi-transparent (`FLAG_CAPTURE_FILL_ALPHA`) rather than solid. The fill's `FLAG_CAPTURE_ELLIPSE_RX`/`RY` (`util/constants.py`) aren't picked freehand — they're derived from `assets/images/ui/objective-pulse.png`'s own largest frame's `get_bounding_rect()` (60×41 source px, an ellipse, not a circle), so the fill matches the pulse ring's own max size/aspect ratio instead of an arbitrary circle sitting behind it. `FLAG_CAPTURE_RADIUS` is defined as `FLAG_CAPTURE_ELLIPSE_RY` (the smaller of the two axes) rather than its own independently-tuned number — they used to diverge (100 vs. a 90×61 ellipse), so the gameplay capture range reached visibly past the fill ring; `is_held()`'s check stays a plain circle (`find_nearest` doesn't do ellipses), and using the smaller axis keeps that circle fully inside the ellipse instead of poking out its narrow sides. `update()` also calls `_spawn_drone()` every frame while uncaptured: on `FLAG_SPAWN_COOLDOWN_MS`, spawns one more drone at a random offset up to `FLAG_SPAWN_RADIUS` from the flag, capped at `FLAG_SPAWN_MAX_CONCURRENT` alive *from that flag* at once (`self.spawned_drones`, pruned of anything with `.active is False` before each cap check, so a dead one frees up a slot for the next cooldown tick). Added because the single guardian `Map.spawn_objects()` spawns at flag creation could die quickly and leave nothing contesting the flag at all — bounded and self-terminating (stops the instant `captured` flips true), not an endless spawner: there are still only 10 flags on the map, each capped, so this adds sustained pressure per objective rather than an unbounded wave system.

`Flag.__init__` takes an optional `tier` (one of `util/constants.py`'s `FLAG_TIERS` entries, or `None` — every direct-construction test uses `None`, which falls back to the pre-tier defaults below unchanged). Added because the flags right next to the first few seconds of the `Tutorial` onboarding overlay were exactly as hard as the ones deep in the map — nothing about a flag's difficulty scaled with how early a player was likely to reach it. `Map._rank_flag_tier_indices()` ranks all 10 flags by distance from `map.spawn_point` into `len(FLAG_TIERS)` (3) roughly-equal bands, nearest first: `"Outpost"` restricts `_spawn_drone()`'s pool to the two cheapest `DRONE_TYPES` and tightens `spawn_max_concurrent` below `FLAG_SPAWN_MAX_CONCURRENT`, `"Bastion"` (farthest) opens the pool back up to every type including `Centipede` and raises the cap above the default — `"Stronghold"` (middle) matches the original untiered numbers exactly, so this is additive difficulty shaping at the two extremes rather than a rebalance of the whole map. Both `_spawn_drone()`'s pool pick and cap check read `self.tier["drone_pool"]`/`["spawn_max_concurrent"]` when `self.tier` is set, falling back to the flat `DRONE_CLASSES`/`FLAG_SPAWN_MAX_CONCURRENT` otherwise. `Map.spawn_objects()`'s *initial* guardian drone (spawned once at flag creation, not through `_spawn_drone()`) also draws from the flag's own tier pool — round-robining within it per-tier (a separate counter per band) rather than randomly, keeping the existing "deterministic, not reshuffled between restarts" property intact (see Win/lose's Restarting section) while still reading as varied within a tier.
- **Obstacle** (`gameplay/map.py`): invisible `Transform`-only collision walls. Spawned from per-tile collision shapes drawn in Tiled's own tile collision editor (`Map.spawn_tile_colliders()`) — no custom tile property needed, `pytmx` parses these natively into `tmx.get_tile_colliders()`. This replaced an earlier approach of hand-drawing a matching rectangle object over every wall tile in a `"wall"` object layer; painting a tile with a collider shape is now enough for every future placement of that tile to collide. Tiled's collision editor mostly produces polygons (auto-traced around a tile's opaque pixels, and often extending slightly past the tile's own bounds so neighboring tiles of the same formation join without seams), but `gameplay/collision.py` only resolves AABBs, so `_collider_local_rect()` takes each shape's bounding box rather than its exact outline — one `Obstacle` per shape, not merged across tiles. A quirk this surfaced: `pytmx`'s map-level object parser walks the whole XML tree for `objectgroup` nodes before it's parsed any tilesets, so an *embedded* tileset's `<tile><objectgroup>` colliders are picked up as nameless pseudo object-layers alongside the map's real `"flag"`/`"spawnPoint"` objects — `spawn_objects()` skips `obj.name is None` to filter those back out.
- **RockObstacle** (`gameplay/map.py`): unlike `Obstacle`, this is *visible* — a real sprite from `obstacles-and-objects.png` (`ROCK_OBSTACLE_FRAME_IDS`, five boulder variants picked randomly per instance) plus a `.rect` that's still a normal entry in `game.walls`, so it blocks movement exactly like any other wall. `Map.spawn_decorative_obstacles()` scatters `ROCK_OBSTACLE_COUNT` of these at load time with a fixed seed (`ROCK_OBSTACLE_SEED`) — positions aren't encoded in the tmx at all, unlike every other spawn method on `Map`. Candidates are rejected if they'd overlap an existing wall, land within `FLAG_CONTEST_RADIUS` of a flag, or land on a fenced compound's floor (`_is_compound_floor()`, checking the map's own pre-rendered pixel color at that point rather than the tile's gid — the compound floor's raw XML gid doesn't match `pytmx`'s internal gid for the same cell once loaded, confirmed by comparing the two directly, so a gid-based check would silently never fire; the rendered pixel is blue-dominant there in a way grass and every other tile used so far isn't). The sheet's boulders turned out to be at frame ids 64-68, not the ids an initial low-res read of a labeled-grid thumbnail suggested — always confirmed with `get_bounding_rect()` per-frame before trusting a read like that, same discipline as every other sheet in this codebase.

### Combat (`gameplay/combat.py`)

Shared hitscan primitives used identically by `Drone.attack()`, `Player.shoot()`/`attack()`, and `Soldier.engage()`/`attack()` — deliberately kept as small near-duplicate `attack()` methods on each attacker rather than a shared base-class method, matching this codebase's existing precedent of duplicating `move()` across `Player`/`Soldier` rather than unifying it.

- `find_nearest(origin, candidates, max_range)` — the targeting primitive every attacker uses to pick *what* to aim at: returns the closest candidate (must expose `.position`; anything with `.active is False` is skipped) within `max_range`, or `None`. "Hitscan" here means this instant nearest-in-range check, **not** a directional raycast — facing/aim is cosmetic everywhere it's used.
- `find_all_in_range(origin, candidates, max_range)` — the AoE counterpart, used once *targeting* has already picked an aim point: same `.position`/`.active` contract as `find_nearest`, but returns every matching candidate instead of just the closest. Only caller today is `Soldier.attack()`'s `Grenadier-Class` splash branch (`self.splash_radius > 0`) — thrown at `find_nearest`'s result, then this collects everyone else caught in the blast around that same point.
- `ready_to_attack(now, last_attack_time, cooldown_ms)` — cooldown gate; `now - last_attack_time >= cooldown_ms`.
- `apply_damage(target, amount)` — decrements `target.hp`, returns whether that killed it (`hp <= 0`), so callers can trigger `target.die()`.
- `raycast(origin, direction, max_range, walls)` — the one genuine directional raycast in this module. Uses `pygame.Rect.clipline()` per wall rather than hand-rolled line/AABB math, returning the nearest of all walls' entry points (a `Vector2`) or `None`. Two callers: `Player.fire_at_nothing()` (see below) uses it directly to decide whether a no-target shot should still leave a wall decal; `has_line_of_sight()` wraps it to gate whether an already-*found* target's ranged attack actually lands.
- `has_line_of_sight(origin, target_pos, walls)` — thin wrapper around `raycast()` capped at the exact distance to `target_pos` (so a wall *behind* the target is never mistaken for one blocking it). Gates every ranged attack (`Drone.engage()`'s fire branch, `Soldier.engage()`, `Player.shoot()`) — melee/splash don't call it, already point-blank or arcing over short cover. *Which* target gets picked is still purely `find_nearest`'s job (walls never factor into targeting); this only decides whether the attack on that target connects.
- `muzzle_position(origin, facing, offset_x, offset_y)` — nudges a `MuzzleFlash`/`LaserFlash`/`Tracer`/`Grenade` spawn point from an attacker's body center (`self.position`) out to a fixed offset that only mirrors with `facing` (`offset_x` negated when facing left, `offset_y` untouched), *not* something that swings continuously toward the target's exact angle. Every `attack()` (`Player`, `Soldier`, `Drone`) calls this before spawning those effects — they used to spawn at `self.position` directly, which read as firing from the character's own torso instead of a held weapon. Went through two wrong designs before landing here: a flat radial offset toward the target (still read as too close to the body), then an offset that scaled `offset_x`/`offset_y` by the normalized aim direction (made the flash visibly orbit the body as the aim angle changed) — both assumed the weapon's screen position tracks the target continuously, but every entity only has two poses at all (`facing` 0/1, see `add_directional_clips`), so the gun's position on the sprite is fixed in sprite-space and only mirrors left/right, it never points up/down. `MUZZLE_OFFSET_X`/`_Y` (24/-6) start from pixel-inspecting `SquadLeader.png`'s and `Assault-Class.png`'s actual fire-frame gun tips (both sit right of center, one also noticeably above it) rather than a guess — the measured baseline (12) still read as too close to the body once actually rendered (the flash sprite's own padding eats into it), so X went through two rounds of bumping up from there (12 → 18 → 24); Y stayed at the measured value. Doesn't touch hit resolution at all: `HitSpark`/`HitSpatter` still land at the target's own position, only the effect's *origin* moves.

Per-attacker tuning lives in `util/constants.py`: `AGGRO_RADIUS`/`DESTROYED_DURATION_MS` are shared by all drones, but `hp`/`speed`/ranges/damage/cooldowns are per-drone-type in the `DRONE_TYPES` dict and per-soldier-class in the `SOLDIER_CLASSES` dict (stored on each instance in `__init__`, not read as module-level globals inside `engage()`/`attack()`); `PLAYER_FIRE_*` stays a flat module-level constant since there's only one player. First-pass numbers, not balanced (see GDD.md).

### Effects (`gameplay/effects.py`)

Purely cosmetic — spawned directly from each attacker's own `attack()`/`die()` (`Player`, `Soldier`, `Drone`), never from `gameplay/combat.py` itself, so combat's pure functions stay testable without a real `Animator`/`SpriteRenderer2D`/display surface. `assets/images/effects/`/`assets/images/projectiles/` have no frame-layout docs (unlike the robot/soldier sheets) — every sheet size/frame-count used here was confirmed the same way as Hornet/Wasp: render it with a grid overlay and inspect it.

- `TimedEffect(GameObject)` — shared base for one-shot sprite-sheet animations: plays a non-looping clip once and sets `self.active = False` once `Animator.is_playing` goes False. `MuzzleFlash`/`LaserFlash`/`HitSpark`/`HitSpatter`/`Explosion`/`BigExplosion` are thin subclasses pinning a sheet/row/frame_count/fps. Unlike the 1-frame `destroyed` clip drones use, these clips have several frames (3–11) and take real time to play through, so gating removal on `is_playing` works cleanly — no separate duration constant needed (contrast `DESTROYED_DURATION_MS`, which exists specifically because a 1-frame clip's `is_playing` goes false almost instantly). `BigExplosion` (`big-explosion.png`, 11 frames @32px) is deliberately a separate class from `Explosion` (`small-explosion.png`, 9 frames @24px) rather than a parameterized size, purely so a Grenadier splash impact reads as visually distinct from a drone dying, not because the two need different logic. `LaserFlash` (`laser-flash.png`, 3 frames @16px, a rounder growing energy-discharge burst) is likewise a separate class from `MuzzleFlash` (`muzzle-flashes.png`, 4 frames @8px) rather than a parameterized sheet — `Drone.attack()` picks between them via each type's `DRONE_TYPES["muzzle_effect"]` (`"gunpowder"` vs `"laser"`), `"laser"` only for Hornet/Wasp since GDD.md describes them as energy-based rather than gunpowder-firing.
- `Tracer(GameObject)` — not sheet-animated; lerps `rect.center` from an attacker's position to a target's over `TRACER_DURATION_MS` using a single static frame (`bullets+plasma.png` frame 0), then deactivates. A visual-only "bullet": since hits are already-instant hitscan (see Combat above), damage is applied before the Tracer even spawns — it never gates anything, purely reads as a shot crossing the screen.
- `Grenade(GameObject)` — `Tracer`'s lobbed counterpart for `Grenadier-Class`: same lerp-over-elapsed-ticks shape, but sheet-animated (spins through `Grenade.png`'s 8-frame tumble via a single `add_directional_clips` row, `GRENADE_SPIN_FPS`) and takes `GRENADE_FLIGHT_MS` (longer than `TRACER_DURATION_MS`) to cross the screen so it reads as thrown, not fired. Also purely cosmetic — the splash damage lands the instant `Soldier.attack()` runs, same convention as everything else.
- `Smoke(TimedEffect)` — `smoke.png`, 8 frames @8px, a puff that grows then disperses into scattered particles. `SMOKE_FPS` is deliberately slower than `EXPLOSION_FPS`/`BIG_EXPLOSION_FPS`, so spawning it at the same position/time as an `Explosion`/`BigExplosion` makes the smoke visibly outlast the fireball rather than needing a separate delayed-spawn mechanism. Wired into `Drone.die()` (once per segment too, for `Centipede`) and `Soldier.attack()`'s `Grenadier-Class` splash branch, always alongside that same call's `Explosion`/`BigExplosion`.
- `BulletImpact(GameObject)` — a static wall-impact decal, the one effect here that isn't sheet-animated at all in the `TimedEffect` sense: `bullet-impacts.png` is 10 unrelated single-frame variants (a scratch/scorch mark), not a clip, so it just picks one at random and holds it for `BULLET_IMPACT_DURATION_MS` before deactivating (elapsed-ticks-driven, same shape as `Tracer`/`Grenade`) rather than fading — long enough to read as lingering, not so long it accumulates unbounded over a session of firing at walls. Only spawned from `Player.fire_at_nothing()` (see the Player entity entry) when `combat.raycast()` finds a wall in a no-target shot's path.
- `FloatingText(GameObject)` — not sprite-sheet based at all (no asset backing it): renders a short string via `pygame.font.SysFont` straight into a `SpriteRenderer2D` image once at construction, then lerps `rect.center` upward by `FLOATING_TEXT_RISE_DISTANCE` and fades it out (`Surface.set_alpha`, mutated on the same cached surface every frame rather than re-rendering the text) over `FLOATING_TEXT_DURATION_MS`, same elapsed-ticks-driven shape as `Tracer`. `offset_index` shifts the spawn sideways by `FLOATING_TEXT_X_SPACING` so two labels spawned at once (`Player.rank_up()` picking 2 stats) don't render on top of each other. Only current caller is `rank_up()` — one instance per stat picked, text/color from `RANK_UP_STAT_LABELS`/`RANK_UP_STAT_COLORS`.
- Wiring: `Player.attack()`/`Soldier.attack()`'s single-target branch (always ranged) spawns `MuzzleFlash` + `Tracer` + `HitSpark` (their targets are always drones); `Soldier.attack()`'s `Grenadier-Class` splash branch spawns `Grenade` + one `HitSpark` per drone hit + `BigExplosion` instead — no `MuzzleFlash`, a thrown grenade has no gun to flash. `Drone.attack()` spawns `HitSpatter` always (its targets are always the player/a soldier), but only adds a muzzle flash + `Tracer` when `self.status == "fire"` — melee has no gun to flash and nothing that should visibly fly across the map — and which muzzle-flash class it spawns depends on `self.muzzle_effect` (`MuzzleFlash` for Scarab/Spider/Centipede, `LaserFlash` for Hornet/Wasp). `Drone.die()` spawns an `Explosion` for all drone types, which incidentally covers Hornet/Wasp's missing destroyed-frame gap with a burst instead. `Player.fire_at_nothing()` (see Player entity entry) always spawns `MuzzleFlash` + `Tracer` even with no target — the gun still visibly fires — and adds `BulletImpact` only if `combat.raycast()` found a wall in the path.
- `gameplay/animation.py`'s `add_death_clip` was generalized into `add_oneshot_clip(obj, path, row, frame_count=1, ...)` (frame_count defaults to 1, preserving the old one-frame behavior for `Drone`'s destroyed clip) so effects.py could reuse it for multi-frame one-shot clips instead of duplicating the clip-building logic.

### Win / lose (`app/game.py`)

`Game._check_end_conditions()` runs every frame from `update()` (which itself short-circuits entirely once `game_over` is set, freezing the sim). VICTORY fires once `self.flags and all(flag.captured for flag in self.flags)` — the `self.flags and` guard isn't a "false victory at startup" latch like the old drones-based check needed (`Map.spawn_objects()` populates `self.flags` synchronously before `Game.update()` ever runs, so it's never actually empty; the guard is just defensive). `self.player.is_dead` is checked first and wins any simultaneous-frame tie, ending the run as GAME OVER instead. `draw()` calls `_draw_end_message()` when `game_over` is set, which blits a translucent overlay plus the centered end-state text over the final frame, plus a smaller "Press any key or click to restart" line below it — there's no separate end-screen panel/scene, just an overlay on top of whatever was on screen.

Restarting: `Game.__init__` was split so everything that needs to reset on a new attempt (entity lists, `Map`, `Player`, `Tutorial`, `game_over`/`end_message`) lives in `restart()`, called once from `__init__` for the first run and called again by `handle_event()` on any key or mouse click while `game_over` is set — app-level one-time setup (cursor, `SplashScreen`, the end-screen fonts/icons) stays in `__init__` itself, untouched by a restart. `handle_event()`'s game-over branch treats almost any key or `MOUSEBUTTONDOWN` as "restart", *except* `_RESTART_EXCLUDED_KEYS` (Escape, F1, F11, a module-level constant not a class attribute — `handle_event()` is tested by calling it unbound against a lightweight fake in `test_game_handle_event.py`, the same pattern `test_game_end_conditions.py` established, and a class attribute wouldn't resolve through a bare `SimpleNamespace` standing in for `self`): Escape already quits via `Application._handle_core_event()` (which always runs before `Game`'s own `handle_event()`), and F1/F11 are meta/dev toggles a player might still want to hit from the end screen without also kicking off a new run. A restart reproduces the exact same map every time (see the `map` subsystem entry above) — `RockObstacle`/wall/flag placement all come from the tmx or a fixed seed, and flag-guardian drone/soldier class picks are a deterministic round-robin (soldiers globally, drones within their flag's own `FLAG_TIERS` band — see the Flag entity entry above) over tmx object order (`Map.spawn_objects()`), not randomized, so nothing reshuffles between attempts. `restart()` itself is tested the same "call it unbound" way, with `Map`/`Player`/`Tutorial`/`FollowCamera` monkeypatched to lightweight stand-ins (`tests/test_game_restart.py`) so the suite doesn't load the real Tiled map on every run — `scripts/smoke_test.py` calls the real thing once for genuine end-to-end coverage.

`_draw_end_message()` also draws two kinds of prompt (Kenney's CC0 input-prompts icons again, `keyboard_any_outline`/`keyboard_escape_outline`/`mouse_outline` loaded once in `__init__`). The restart prompt always shows via `_draw_icon_caption(icon, caption_parts, top) -> bottom`: a big (96px) `keyboard_any_outline` icon centered on top, with a short caption below it built by `_build_inline(parts)` — `parts` mixes strings (rendered as text) and icon surfaces inline, so the caption reads "or [mouse icon] to restart" with an actual `mouse_outline` icon standing in for the word "click" rather than spelling it out; the icon (not `mouse_left_outline`) is deliberately button-agnostic since restarting fires on *any* mouse button, not just left click. A second, smaller "Press [ESC] to exit" line *only* shows when `end_message == "VICTORY"`, via the older `_draw_prompt_line(icon, text, top) -> bottom` (small icon beside plain text, no inline mixing needed) — Escape already quits regardless of which screen is showing, this second line is purely telling the player that on the screen where they're more likely to just be done rather than itching to retry. Both drawing methods return their bottom y so a second line can stack directly under the first without hand-tuned spacing. Tested the same unbound-fake way (`tests/test_game_end_message.py`): `_draw_icon_caption`/`_draw_prompt_line`/`_build_inline` are stubbed or bound as plain attributes on the fake instance (not monkeypatched on the `Game` class) for the same reason `_RESTART_EXCLUDED_KEYS` had to move off the class — a bare `SimpleNamespace` standing in for `self` never resolves attributes through `Game`'s own class hierarchy.

### UI / HP bars (`gameplay/ui.py`)

Three free functions, no classes:

- `draw_bar(surface, camera, world_pos, width, height, fraction, fill_color, back_color=(0,0,0))` — the generic linear primitive: a black backing rect plus a proportionally-filled colored rect, centered on a world position and run through `camera.scaled()`/`camera.world_to_screen()` so callers don't touch camera math directly.
- `draw_radial_progress(surface, camera, world_pos, radius_x, radius_y, fraction, fill_color, back_color=(0,0,0), segments=32, alpha=255)` — the circular/elliptical equivalent: a filled pie-slice sweeping clockwise from 12 o'clock, built as a `pygame.draw.polygon` fan of points around the arc (`center` + `steps` points, `steps` scaled by `fraction` so a small wedge doesn't waste segments; each point uses `radius_x`/`radius_y` independently, so it doesn't have to be a circle — pass equal values for one). `fraction >= 1.0` short-circuits to a plain `pygame.draw.ellipse` (a polygon fan can't close a full 360° sweep on its own). Everything renders onto a small `pygame.SRCALPHA` scratch surface first, then blits that onto `surface` — `pygame.draw` ignores a color's alpha channel on a target without per-pixel alpha (the game window included), so `alpha < 255` needs this indirection to actually blend (same trick `Game._draw_end_message()` uses for its overlay). Used by `Flag._draw_capture_progress()` (fixed green, `FLAG_CAPTURE_ELLIPSE_RX`/`RY`, `alpha=FLAG_CAPTURE_FILL_ALPHA`, drawn centered on the flag *before* the pulse ring and the flag's own sprite, so it reads as a translucent ellipse growing behind the flag rather than a bar floating above it — sized/shaped to match the flag's own pulse animation, see the Flag entity entry above).
- `draw_health_bar(surface, camera, rect, hp, max_hp, always=False)` — built on `draw_bar`: computes `fraction = max(0, hp) / max_hp`, colors it by tier (`HP_BAR_HEALTHY`/`HURT`/`CRITICAL` in `util/constants.py`, thresholds at 60%/30%), and positions it at `(rect.centerx, rect.top - HP_BAR_GAP)`. Returns early (draws nothing) at full health unless `always=True` — `Player.draw_health()` passes `always=True` (HP is worth seeing proactively, not just after the first hit), `Soldier`/`Drone.draw_health()` don't (a screen full of undamaged units doesn't need a wall of full bars; a bar appears the moment something takes its first hit). `Drone.draw_health()` additionally skips entirely while `status == "destroyed"` — no bar over a wreck.

`Game.draw()` calls `soldier.draw_health()`/`robot.draw_health()` for everything in `self.soldiers`/`self.robots` each frame (after the main `all_sprites` draw loop, so bars layer on top), plus `player.draw_rank()`/`player.draw_health()` same as before.

### Tutorial (`gameplay/tutorial.py`)

`Tutorial` is a linear "press this key" onboarding overlay for a run's first few seconds — plain screen-space HUD, not a `GameObject` (no world position, not in `game.all_sprites`); `Game.__init__` constructs one `self.tutorial`, and `update()`/`draw()` call into it explicitly, same wiring style as `_draw_end_message()`. `TUTORIAL_STEPS` is a fixed 3-step sequence (`MOVE` → `FIRE` → `SQUAD STANCE`), each entry pairing a label, one or more icon-name **groups**, and a `check(game) -> bool` predicate; `Tutorial.update()` advances `step_index` the instant the current step's predicate is true, and both `update()`/`draw()` become no-ops once `step_index` reaches the end (`done`). Each check fires on the raw input happening at all, not on the corresponding game action landing — `FIRE` completes the moment the left mouse button goes down, not once a shot actually hits a drone, since one might not even be in range the first time the player tries; gating on a successful hit could leave the prompt stuck indefinitely through no fault of the player. "Not persistent" here means only "gone for good once completed this process" — there's no save/load yet (see Persistence below), so nothing needs to remember it was already shown across runs. Icons are Kenney's CC0 input-prompts pack (see ASSETS.md) rendered via `pygamine.image.load_image(ImagePath(name, "input_prompts"), size=...)` — only the "Default" keyboard/mouse style is bundled (`assets/images/input_prompts/`, ~1000 files' worth of every key/mouse-button icon in that style, not just the ones actually used, so a later step can reuse the same folder for free), skipping every gamepad platform folder and the Double/Vector/Fonts variants the source pack also ships, since this game has no gamepad support to prompt for.

`MOVE`'s `"groups"` has two entries — a WASD tuple and an arrow-key tuple, since either moves — joined by an "OR" connector; `FIRE`/`SQUAD STANCE` each have exactly one group. `Tutorial._build_group(names)` renders a 4-name group as a physical keyboard cross cluster (`names[0]` centered on top, `names[1:]` in a row below it left-to-right) — the same arrangement WASD and the arrow keys actually sit in on a real keyboard, which is why both read correctly with the exact same layout code — and anything else (the single-icon FIRE/SQUAD STANCE groups) as a plain row. `Tutorial._build_content(step)` lays every group in `step["groups"]` out left-to-right at `TUTORIAL_GROUP_GAP` spacing, inserting a rendered `"OR"` between groups only when there's more than one (`FIRE`/`SQUAD STANCE` never show a connector). `draw()` builds one small `SRCALPHA` panel (translucent black backing, current step's label centered on top, `_build_content()`'s result centered below) and blits it top-center each frame — cheap enough to just rebuild from scratch every call rather than caching, since it only renders at all for the first few seconds of a run.

### Collision

`gameplay/collision.py`'s `collide(mover, direction, walls) -> bool` is a single-axis AABB push-out: called once for `'x'` and once for `'y'` per moving entity per frame (see `Player.move()` / `Soldier.move()` / `Drone.move()`), returning whether it actually pushed against a wall. Resolves against the first overlapping wall only (not all of them), zeroes the corresponding velocity axis, and nudges the mover's `hit_rect` edge 0.1px past the wall's edge. `hit_rect` is a separate, smaller `pygame.Rect` from the sprite's visual `rect` — collision uses the former, rendering the latter.

`move()`'s authoritative position is `self.position`, a float `Vector2` — `hit_rect` (an int-only `pygame.Rect`) is written from it fresh each axis purely to run that axis's overlap check, and is folded back into `self.position` *only* when `collide()` returns `True`. Two bugs already got caught and fixed here, both worth knowing about before touching this code again:
- Updating `self.position` from velocity but never writing a wall's `hit_rect` correction back to it (only to the throwaway `hit_rect`) meant push-outs were silently discarded every frame — holding a direction key long enough walked straight through any wall.
- Making `hit_rect` itself the persistent per-frame accumulator (to fix the above) instead of resyncing from `self.position`'s float value made *every* frame's sub-pixel remainder get silently truncated away by `pygame.Rect`'s integer storage — and asymmetrically: repeatedly flooring `int + v` for a positive `v` advances by `floor(v)` per step, while repeatedly flooring `int - v` advances by `-ceil(v)` per step, so the negative direction on each axis (left, up) consistently outran the positive direction (right, down). Feeding `hit_rect` back into `position` only on an actual `collide()` hit avoids both: no wall, no truncation.

`collide()` itself is still passed a plain wall list — `nearby_walls(game, hit_rect)` is what changed, and it's called once per `move()` (not once per axis) before either collision check: it queries `game.wall_grid` (`pygamine.spatial_grid.SpatialGrid`, the same primitive `standoff`'s `Entity.move()` already uses) for the cells around `hit_rect`, inflated by a full cell on every side so a wall the mover crosses into partway through this frame's movement is still in the candidate set, and falls back to the flat `game.walls` list if no grid is set (every test in this suite constructs `Player`/`Soldier`/`Drone` against a bare `FakeGame` with no `wall_grid`, so none of them needed to change). `game.wall_grid` is built once per `Game.restart()` (`SpatialGrid.of_static(self.walls, max(self.map.tile_width, self.map.tile_height))`), right after `Map()` finishes building every wall — walls never change for the rest of that run (tile colliders + `RockObstacle`s, nothing ever removes one), so there's no reason to rebuild the grid more than once per attempt. This replaced scanning the *entire* wall list twice (once per axis) for every `Player`/`Soldier`/`Drone` every frame, an `O(movers × walls)` cost that GDD.md's line-of-sight balance pass (item 22) caught degrading over a long session as `Flag._spawn_drone()` grew the drone count — measured directly (not just theorized) at ~291ms/frame with 310 drones and 467 walls before this fix, ~6ms/frame after (~47x).

### Animation

`gameplay/animation.py` has the shared helpers every entity's `__init__` calls: `add_directional_clips(obj, sheet_path, {"clip_name": row, ...})` slices frames from a sprite sheet and registers both a right-facing clip (`"{name}_0"`) and a horizontally-flipped left-facing clip (`"{name}_1"`) on the object's `Animator` component. Entities play `f"{self.status}_{self.facing}"` each update — `facing` is 0 (right) or 1 (left), never re-derived from velocity direction (it's set directly in each entity's `walk()`).

### Assets

No `AssetManager`/manifest — `ImagePath(name, folder)` (from `pygamine.asset_path`) builds `assets/images/{folder}/{name}.png` directly; sprite sheets are loaded straight off disk via `pygamine.sprite_sheet.SpriteSheet.from_path`. See [ASSETS.md](ASSETS.md) for the source/license of the bundled gameplay art (mattwalkden's Free Robot Warfare Pack — commercial-use-safe, unlike some of this developer's other early projects). `assets/images/branding/` is separate from that pack: `pygame_logo.png` is the same file chokepoint/highrise/hunted/standoff all bundle, and `title.png` is AI-generated key art (iterated over several passes — palette-matched to the real `SquadLeader`/`Scarab` sprites rather than pixel-copied from them, since the in-game sprites are top-down and read poorly reused as a side-profile icon). A misleading placeholder copyright/year and a rendering-artifact smudge were inpainted out cleanly; the image tool's own watermark wasn't — patch-cloning/feathering/mirror-tiling all left a faint seam under close inspection, so it's cropped off the canvas's right edge instead (past where any real content extends, confirmed empty first) rather than papered over.

All image folders live under `assets/images/{folder}/`, lowercase, matching the sibling projects' convention (`effects`, `projectiles`, `obstacles_and_objects`, `robots`, `soliders`, `tileset`, `ui`) — `gameplay/effects.py` uses `ImagePath` like everything else now; it used to reach outside `assets/images/` with the plain `AssetPath(name, folder)` before `assets/Effects/`/`assets/Projectiles/` were moved under `assets/images/`.

Asset folders/files that exist but aren't wired into any code yet: `big-fragments`/`small-fragments` in `assets/images/effects/` (see GDD.md's Effects & projectiles section for what each would need — everything else in that folder is now used, including `bullet-impacts.png`: see `BulletImpact`/`combat.raycast()` above, the "needs a raycast against `game.walls`" gap this used to be blocked on is closed), `assets/images/projectiles/RPG-round.png` (`Grenade.png` is now used by `Grenadier-Class`), and most of `assets/images/obstacles_and_objects/obstacles-and-objects.png` (only its five boulder frames are used, see the `RockObstacle` entry above — the streetlamp, barrels, crates/debris, glass/window wall fragments, and the whole car/wreck section are still unused). All 5 wired-up drone types (including Centipede now, see above) and all 6 soldier classes (including RadioOperator now, see above) are covered. See GDD.md's content-inventory table.

None yet. No save/load, no `SaveStore` usage (unlike chokepoint). `/saves/` is gitignored proactively in case this gets added later.
